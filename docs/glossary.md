# hopper glossary

The application's words. Code, tests, events, API fields and UI use these and no
synonyms. Rename here first, in the same commit as everything else.

| term | meaning | not |
|------|---------|-----|
| **Job** | One unit of work pushed through the API: an executor name, a payload, a priority. | task, run |
| **Priority** | `0..100` on the job, higher first. Default 50. | rank |
| **Backburner** | The `hopper:backburner` label on an issue: the GitHub sources never pick it up while it is set, and cancel a waiting job whose issue gets it. Not a priority. | paused (*parked* is a job a person took out of its lane) |
| **Effective priority** | Priority after the router's boost (cheap advice), which applies only in active mode, or the resume boost of a job resuming with an answer. The decider's notion (`effectivePriority`, `src/decider/assign.ts`); the queue sorter is given it. | score |
| **Queue sorter** | The role that orders the waiting jobs (`QueueSorter` port: `sort(entries) → job ids`). Live, exactly one instance (the plugins config's `queueSorter`; absent → the built-in `priority`). Built-in plugins `priority` (effective priority, then oldest, then id — the decider's own rule), `oldest-first`, `newest-first`. It orders, and it is the **pre-sort**; it never holds. One that cannot run, throws, or returns anything but distinct waiting job ids → `priority` answers, `fallback` in `/api/plugins`. | scheduler, ranker |
| **Queue gate** | What a new job passes before it may run (issue #159): every job a source creates waits **unaccepted** until the pre-sort or the user **accepts** it, or is **rejected**. A user's setting (`QueueGate`): mode `auto-accept` (default: the pre-sort is applied before each Decision as jobs arrive) or `review` (each job waits for the user), and `autoAcceptPerHour`, the throttle (null: no limit; past it a new job waits for the user). The Queue view; `POST /ui/api/queue-gate`. | intake filter, approval (*approve* is the router's) |
| **Pre-sort** | The queue sorter over the unaccepted jobs (`PreSort`): their order (the Queue view's Pre-sorted column) and the ones it rejects, each with a reason (the sorter's optional `reject`). **Accept pre-sort** applies it at once: rejects what it rejects, accepts the rest. | triage, presort ranking |
| **Accepted** (job) | Let through the queue gate (`job.accepted`, `by` `pre-sort` or `user`). An **unaccepted** job (`accepted: false`) is waiting, held `awaiting acceptance`; a job from before the gate is accepted. Not *approved*: approving overrides router holds and never passes the gate. | admitted, approved |
| **Rejected** | Status `rejected`: a waiting job turned away at the queue gate by the user (UI Reject) or the pre-sort. Ended, kept, never run — neutralized, not deleted; its reason is its `error` — the user may give one (UI Reject's reason field, issue #387), else `rejected by the user`. On GitHub nothing is written (issue #387): the issue is not taken again until it is **assigned** to the user again after the rejection, or the user runs it again. A `hopper:rejected` label from before still keeps an issue out while set; removing it offers the issue again (a re-run). | declined, dropped, deleted |
| **User order** | The order the user gives the waiting jobs in the Queue view (`POST /ui/api/queue/order`): each job's `userRank`. It orders jobs of one effective priority only (issue #461): within each priority, ranked jobs come first, by rank, then the rest in the sorter's order; a ranked job never goes ahead of one of higher priority. Moving an unaccepted job into it accepts the job. | manual order, pins |
| **Hopper name** | A GitHub source's `hopperName` option: which hopper this is when several watch one GitHub (issue #159). An issue labelled `hopper@<name>` is **addressed** to the hopper of that name: only that one takes it; an issue addressed to no hopper goes to any (the first claim wins). A source with no name takes no addressed issue. | instance name, hopper id |
| **Queue order** | The queue sorter's order of the waiting jobs for one Decision (`DecisionInputs.queueOrder`: sorter instance + job ids). Step 6 orders admissible jobs by it; jobs it leaves out follow by the decider's own rule. `/api/queue` `waiting` is in the same order. | ranking |
| **Machine** | A host that can run jobs: this laptop (`local`) and every attached machine. Each is a `machine-source` instance in the plugins config's `machines` (issue #74), named after the instance (the machine id): this one of the built-in plugin `local` (its `lanes` option is the lane count, its optional `executors` option narrows what runs here, its optional `session` names the herdr session its jobs run in, which the hopper starts — issue #260), an attached one of `ssh`, `docker` or `client`. One that cannot run lists no machine; the others still run what they list. The hopper does not register its own host by default: a fresh plugins config lists no machine, and this one is added like any other (issue #259). The container is not a machine: with `HOPPER_LOCAL_MACHINE=false` there is no `local` instance (issue #141). | node, worker |
| **Attached machine** | A target beside this machine: a machine-source instance of the plugin named by its **connection** — `ssh` (an **ssh target**'s host, running jobs in its own herdr session, or with `herdr: false` none: Cursor and commands only, online while it answers over ssh, issue #142), `docker` (a **container target**) or `client` (a **client target**) — followed without a restart (issue #74). Online while that herdr session answers, or that container runs. A client target joins itself with a **join line** (issue #308); an ssh target is attached from the UI by a **machine edit**; its name, lanes, executors, label and connection details edited, and it removed, like any plugin instance (a new name: the options edit's `rename`, issue #205). | remote, worker, consumer |
| **Target** | The role of an attached machine: a machine the hopper connects to and runs jobs on. "Backend" is the same role; code, docs and UI say target. | consumer, client |
| **Connection** | How the hopper reaches a machine to run a job there: none (this machine, plugin `local`), ssh (plugin `ssh`), docker exec (plugin `docker`), or a client's tunnel (plugin `client`). One per attached machine, which names its machine-source plugin; each authenticated as **target authentication** says. The machines API (`GET /api/machines/config`) gives each machine's `connection`, never `plugin` (issue #206). | protocol, transport |
| **Target authentication** | How the hopper proves itself to each kind of target, and the target to it (issue #59, design.md "Target authentication"): an ssh target by the **hopper's ssh key** alone to a **pinned host key**; a container target only through a **docker socket** of the hopper's own; a client target by its **client token**, derived from the **link keys**. Never a password. | target auth, credentials |
| **Hopper's ssh key** | The key the hopper offers an ssh target: the mounted secret file `HOPPER_SSH_KEY_FILE` names, alone; none mounted, the hopper's own (issue #293) — minted once, kept in the user's store, written to `<workdir>/ssh/hopper_ed25519` at each start, its public half shown in the Add machine form —, then the key files `ssh -G` names that exist. Installed on a target with `restrict`. Never the user's agent. | identity, deploy key |
| **Pinned host key** | An `ssh` instance's `hostKey` option in the plugins config (`<type> <base64>`): the only host key the hopper accepts from it, written to its own known_hosts under the target's name. Taken from the user's own `~/.ssh/known_hosts`, or the **host key offer** the person confirmed (issue #293); never learned from a connection unseen. Absent → the hopper does not connect. | known host |
| **Host key offer** | The host key a new ssh target would be pinned to, with its SHA256 fingerprint (`POST /ui/api/machines/host-key`, issue #293): the one `~/.ssh/known_hosts` holds (`known`), else the one the target presents now, which the person checks on the machine and confirms; only then is it sent with the machine edit and pinned. | fingerprint prompt, TOFU |
| **Docker socket** | The socket the hopper reaches docker through, named by `HOPPER_DOCKER_HOST`: a unix socket only its own user may open, in a directory only it may change — in practice the **docker socket proxy**. Never the root daemon's socket (the unit hides it). | DOCKER_HOST |
| **Docker socket proxy** | An allowlisting proxy (`wollomatic/socket-proxy`, pinned by digest) in front of the root docker socket that lets through ping, inspect and exec on the named container targets only (`scripts/docker-proxy.sh`; the allowlist is `proxyAllowlist`). | socket proxy |
| **ssh target** | The ssh destination of an attached machine: a `~/.ssh/config` alias or a plain `user@host` — typed in the UI too (issue #293), so a hopper with no `~/.ssh/config` can attach one. | host |
| **Container target** | An attached machine that is a running container on this machine's docker, reached through `docker exec` (`docker:` names the container), not ssh. No agent and no herdr runs in it: it runs commands only (issue #58). | sandbox, docker host |
| **Job shape** | How a job's work is done (issue #316, design.md "Job shapes"): **sandboxed** — an executor the hopper runs, in a **container sandbox**; the primary shape — or **operator-led** — by hand in an IDE such as Cursor, no executor. Both are claimed once per issue and checked in by the closing pull request. | job type, job kind |
| **Container tool** | Podman or Docker: the tool whose commands the update notice and Settings → Version show for a container install's update (issue #521). Chosen per browser, Podman until Docker is chosen; the hopper does not detect it. Not the engine. | engine, runtime |
| **Container sandbox** | A container, on Podman or Docker, that confines a sandboxed job the hopper runs: the primary, enforced sandbox path (issue #316). Not built yet (#314, #308). Neither a container target (commands only) nor an agent box (a test machine, not locked down). | jail, VM |
| **Agent box** | A container on this machine's docker with one agent CLI in it (claude, codex, cursor, omp, opencode) (issues #295, #307): an ssh target with its own herdr session, made by `scripts/agent-boxes.sh`, on the hopper's network when the hopper runs in a container, and attached like any machine over ssh — never a container target. Attached running its agent's executor. | test container, sandbox |
| **Pickup** | An issue taken up by hand at an agent box — a person in a terminal, or an IDE agent — reported in the box's **pickup record** (issue #319, design.md "Pickups on agent boxes"). It starts `picked-up`, then reports `working`, `waiting`, `blocked`, `pull-request`; `finished` or `released` ends it. **Stale** when not heard from past the stale time. Not a claim: a claim is the hopper's. | session, check-in, lease |
| **Pickup record** | One JSON file per issue in a box's pickup dir (`HOPPER_PICKUP_DIR`, else `~/.hopper/pickups/`): the pickup's state, its heartbeat (`updatedAt`) and its history, each entry with a `seq` that only grows. Written by the box (`hopper-pickup`), read by the hopper side over ssh; the box sends nothing. | status file, report |
| **Operator-led** | The job shape beside sandboxed (design.md "Job shapes"), and the mode of a pickup: work done by hand — a person at a terminal, or an IDE or its agent the hopper has no pane in — not by an executor the hopper runs. Status `operator_led` (issue #318): a waiting job an operator claimed in the UI (`POST /ui/api/jobs/:id/operator-led`, event `job.claimed_by_operator`). It holds no lane and the decider never runs it; its issue keeps `hopper:claimed`; its source finishes it when the work is complete (`JobSource.notComplete`: its closing pull request reached the completion), and it is cancelled as any job is. Shown in the Overview's Operator-led list and on the lane timeline's own `operator-led` row. | handjammed, manual, IDE job, interactive |
| **Operator-led claim** | Claiming a waiting job as operator-led (`job.claimed_by_operator`): the hopper's record that someone took its work by hand. Distinct from a lane claim (`job.claimed`, a Decision's) and from the claim of an issue (the label). | handjam, check-in |
| **Client target** | An attached machine that runs the **hopper client** and dials in to this hopper's own URL (issue #308): herdr calls go down its **link** over HTTP/2, signed with its **client token** (`client: { key }`, its **machine key**, issue #59). Added by **joining** with a **join code**. Its herdr binary and session are its own. Online while its herdr session answers the hopper's signed calls. | agent, remote client, backend |
| **Hopper client** | The program a client target runs (`src/client/`, installed as plain files by the hopper's install script `/client/install`, unit `hopper-client`, or baked into a **sandbox box**): joins with a **join line**, dials in, serves `POST /herdr` (and, for `claude-plan`'s usage readings, two read-only `claude` calls, `POST /claude`, issue #366; for an escalation level, one locked-down print-mode `claude` run, `POST /level`, issue #482) for requests signed with its token, signs its answers, dials again when its link ends. It runs a **client release** the hopper loads onto it. | agent, daemon |
| **Client release** | The hopper client as one versioned unit (issue #70, `src/client/release.ts`): its files, its **manifest** (each file's SHA-256) and an id from the manifest; the manifest, not a list in the client, names its files (issue #545). Released from the hopper — the client files of the install it runs — and loaded onto each client target whose client runs another (`POST /load`), never while a job runs there. | client version, client build, client update |
| **Bridge** (release) | The release the hopper loads onto a client released before manifests, which checks a fixed list of file names (issue #545, `src/machines/client-bridge.ts`): exactly that list's names, the id that client computes; its `main.ts` writes the hopper's client release over the install dir and restarts. | shim, stub release, upgrader |
| **Link** | A client target's connection to the hopper (issue #308): the socket its client dialled in on, an HTTP/1.1 upgrade to `hopper-client/1` at `/client/connect` on the hopper's own URL, signed with the client token; HTTP/2 flows on it, the hopper's calls going down it. One per machine; dialling in again replaces it. | tunnel, reverse tunnel, websocket |
| **Join code** | A one-time code that adds one machine (issue #308): minted by an admin's **Add machine** (`POST /ui/api/machines/join`) or `hopper join-code`, for 10 minutes, kept only hashed; spent by the machine's join (`POST /client/join`). | pairing code, registration token, invite |
| **Join line** | `<hopper URL>#<join code>`: what a machine joins with. Add machine shows it inside the one line to run — the install script's pipe for a computer, the `run` of a sandbox box. | join URL, invite link |
| **Link key** | An X25519 key each end of a link holds (issue #308): the machine's in its client dir (`link-key.pem`, mode 600), the hopper's for each user in that user's schema. The client token is derived from one end's private half and the other's public half, the same on both ends. Never sent but its public half. | keypair, device key |
| **Machine key** | The public half of a machine's link key: who a client target is (`client: { key }`), recorded when it joins. A removed machine's key dials in no more. | device id, node key |
| **Sandbox box** | A client target that is a locked-down container on the computer the hopper runs on, from the published image `ghcr.io/henningfutrell/hopper:box-<agent>` (`scripts/box/`): every capability dropped, no new privileges, a read-only root, its home a volume of its own, nothing of the computer mounted, on the hopper's compose network. The sandboxed job shape's machine. Not an **agent box** (an ssh target, for testing). | sandbox, container machine |
| **Client token** | What a client target and the hopper sign with (issue #59): derived on each end from its **link key** and the other end's public half (issue #308), so neither stores it and it never crosses the wire: each request carries an HMAC of it, and each answer too. | API key, bearer token, password, shared secret |
| **Print-mode agent executor** | An executor that runs an agent CLI in print mode on the job's machine, one run per turn, reading the hopper protocol's marker from its last message (issue #307): `cursor-agent`, `codex`, `opencode`, `omp`, and `claude` (issue #533: Claude Code in print mode, which shows no startup screen). A question pauses the job with the agent's session id, the answer resumes that session. Never idempotent; nothing to reattach. | headless agent, batch agent |
| **Cursor executor** | The built-in `cursor-agent` executor plugin (issue #142), a print-mode agent executor: one job is Cursor's CLI agent (`cursor-agent -p`) on the job's machine — this one or an ssh target, never a container or client target — in the job's work tree, one print-mode run per turn. The job prompt carries the hopper protocol; a question pauses the job with its **Cursor chat** id, and the answer resumes that chat (`--resume`). Never idempotent; nothing to reattach. Cursor signs in on each machine; the hopper holds no Cursor credential. | cursor runner |
| **Shipped plugin** | A built-in plugin (`src/plugins/builtin.ts`). One of a list role other than `machine-source` and `escalation-level` (edited in Question gates alone, issue #444) is **enabled** while an instance names it and is switched on or off in the Plugins view: on adds one instance under the plugin's id with its defaults, off removes its one instance (issue #142). A switch, not an options form (owner decision); installing other plugins from a store URL is a later issue. | built-in, bundled plugin |
| **Cursor chat** | Cursor's session of one job (`session_id` of its JSON result): what a question's answer resumes. Kept in the job's executor state. | chat id, conversation |
| **Command executor** | The built-in `command` executor plugin: runs a job's `body` (its first fenced code block, else all of it) with `sh -c` on the job's machine, through that machine's connection, and finishes with the exit code and output; a non-zero exit fails the job. Never idempotent, never asks. | shell executor, runner |
| **Detected ssh target** | A `Host` alias of `~/.ssh/config` (patterns excluded, `Include` followed): offered by the Add form; a machine edit also takes a typed plain `[user@]host` (issue #293). | known host |
| **Machine edit** | Attaching an ssh target from the UI (`POST /ui/api/machines`): a new `ssh` instance in the plugins config's `machines`, against its `version`. Without an ssh target it adds this machine (issue #260): a `local` instance under the name given, with the herdr session named (default `hopper`), started by the hopper first; refused while a machine is this one already, and in a container, which is not a machine (issue #275). An ssh target that is this machine — ssh would reach this host as the hopper's own user on port 22 — is added as this machine too, with no ssh (issue #275). Sets `ssh` to a detected ssh target or a plain `[user@]host`, `hostKey` only to a confirmed **host key offer** (else the daemon pins the one known_hosts holds, issue #293), never `session`; herdr is called by name there, from its PATH then `~/.local/bin`, so no herdr path is stored (issue #311). Lanes and executors left out are the **machine defaults**; it runs herdr (`herdr`) only when one of its executors is a herdr-claude instance (issue #142). Editing (its name too: `rename`, issue #205) or removing a machine is a plugins edit (`POST /ui/api/plugins`, issue #74). | machine config |
| **Machine defaults** | What a machine attached from the UI starts with: its lanes and the executors it runs — the plugins config's `machineDefaults` (`lanes`, `executors`), edited in the Machines view (`POST /ui/api/machines/defaults`, issue #142). A field left out is the `ssh` plugin's own default: one lane, `herdr-claude`. Never changes a machine already attached. | default machine, template |
| **Lane** | One concurrent job slot on a machine. Opened and closed by Decisions. `idle`, `busy`, `draining`. | slot, worker, thread |
| **Draining** | A busy lane the Decision wants gone; it closes when its job ends. Its job runs on untouched: the UI shows it busy, "closes after this job" (issue #381). | |
| **Usage reading** | One budget measurement: `used` of `limit` in a `unit`, optionally for one machine (a machine with throttling readings of its own is capped by those alone: its own account, e.g. claude-plan's `machine` option, issue #139; every claude-plan reading has one, this machine's as `local`, issue #174), optionally limiting the jobs of some executors only (`executors`; absent: every job), optionally of one usage window, optionally informational. Supplied by usage sources: the `usage-source` role's 0..n instances (the plugins config's `usageSources`; an absent section → the built-in `claude` instance of `claude-plan`; `command-usage` reads any agent framework's; the fake is a test double). | quota |
| **Agent framework** | The agent CLI a job runs in: Claude Code, Codex, Gemini CLI and others. One executor plugin per framework (`herdr-claude` and `claude` are Claude Code's, `cursor-agent` Cursor's, `codex`, `opencode` and `omp` theirs); a usage reading limits the jobs of one framework's executors, never another's (issue #140). | provider, model, backend |
| **Usage window** | The period a usage reading measures, as its source names it (`window`): claude-plan's `session` (5 h), `week` (all models), `week (Fable)`. | period, bucket |
| **Informational reading** | A usage reading that is shown but never throttles lanes (`informational: true`): its budget limits one model, not every job — claude-plan's `week (Fable)`, or a window it does not know. The decider's step 1 skips it. | advisory |
| **Usage sample** | A usage reading as the **usage history** keeps it (issue #385): its time (`at`, when the source read it), source, machine, usage window, used, limit, unit, `resetsAt`, informational, and the account's identity. Kept once per source, machine, usage window and time, so once per read. `UsageSample`. | data point, record |
| **Usage history** | Every usage sample of one user, in their user schema (`usage_samples`), recorded from every usage source each minute (`src/usage/history.ts`); the usage graph reads it. Survives restarts and container recreates; pruned past the history retention. | metrics, time series, log |
| **Machine sample** | One machine's resources at one time, as the resource recorder keeps them (issue #560): CPU busy, load, cores, memory total and available, swap, disk free and total, its lanes in use and its lane cap. Kept once per machine and time, every minute while the machine is online with a reading. `MachineSample`. | metric, data point |
| **Resource recorder** | The part of a user runtime that keeps a machine sample of each of the user's machines every minute (`src/machines/history.ts`, `machine_samples`), pruned past the history retention. | collector, agent, exporter |
| **Resource graph** | A graph of machine samples over the graph range (issue #560): per machine and resource step, the peak share of CPU busy, memory used, swap used, disk used and lanes in use, with a gap where the machine gave no sample. One machine's on its Machines card (*Resources over time*), every machine's on the Usage page. `GET /api/machines/history`, `GET /api/machines/:id/history`. | dashboard, monitoring |
| **Resource step** | The time one point of the resource graph stands for; finer than the graph step: 15 minutes up to a day, an hour up to 4, 6 hours up to 14, a day up to 60, else a week. | bucket, resolution |
| **History retention** | How many days usage samples and machine samples are kept (default 90): the user's setting, an admin's to change (the Usage view). Older samples are deleted every hour, and at once when it is lowered. | TTL, expiry |
| **Usage graph** | The overview panel *Usage over time*: one line per account and usage window — one line however many machines read the account (issue #502), per graph step the highest of their readings, since they read the same limit — named by the account and the window, one colour per account, session solid, week dashed, informational dotted (hidden until shown from the legend) — over the graph range at the graph step, drawn like the KPI cards' sparklines. Zoomed by its buttons, a pinch, Ctrl/⌘ + scroll or a drag across; Reset goes back to the graph range. A gap where no source of the account gave anything, a tick at the axis foot where a window reset. Redrawn as new usage samples are kept (SSE `usage.recorded`). `GET /api/usage/history`. The instance admin's, summed over every user, is in Settings → Users (`GET /api/instance/usage-history`). | chart, dashboard |
| **Graph range** | The stretch of time the usage graph shows: a preset ending now (`24h`, `3d`, `7d`, `30d`; default `7d`), the user's choice, kept by the hopper (`usageGraphView` setting); or a stretch zoomed to, for that page view only. | window (a usage window is a reading's), period |
| **Graph step** | The time one point of the usage graph stands for: the highest share of the limit used in it. It follows the graph range (issue #502): an hour up to 2 days, 6 hours up to 4, a day up to 60 (the default week is per day), else a week. Day and week steps start at the viewer's midnight, weeks on Monday. | bucket, resolution, period, grain |
| **Account** | Who a part acts as on an outside service: the Claude account a usage source reads usage for (email, plan), the GitHub App bot the `github-app` source acts as and its installation repos, the **connected account** a `github-account` source acts as. `GET /api/accounts`. Facts only, never a token. | identity (in UI copy), credentials |
| **Lane effect** | What usage does to one machine's lanes now: per executor it runs, the used fraction, lane cap and band (`free`, `soft`, `hard`, `offline`) — the decider's steps 1-2 over the readings that limit that executor — and the machine's own, its least limited executor's. `GET /api/usage` `machines`. | |
| **Soft limit / hard limit** | Usage fractions. Past soft, the lane cap scales down; at hard, lanes stop. Together the **usage limits**: the user's, set on the Usage view and stored (issue #522), else `HOPPER_SOFT_LIMIT` / `HOPPER_HARD_LIMIT`. Below soft is the **free** band, from soft to hard the **soft** band, at hard and above the **hard** band. | thresholds, throttle bands |
| **Lane cap** | The most lanes a machine may run given its usage; an executor's lane cap, the most its jobs may hold there. | |
| **Usage pacing** | How the decider spends each account's usage against the time left before its usage windows reset (issue #373): the burn window, placement pressure and the critical priority. `DeciderPolicy.pacing`. | |
| **Week window** | A usage window whose name starts with `week` (claude-plan's `week`; `weekly`): the one the burn window applies to. A session window never burns. | |
| **Burn window** | The hours before a week window's `resetsAt` (`HOPPER_BURN_WINDOW_HOURS`, default 18; 0: off) in which that window stops throttling unless it is spent: what is left would be lost at the reset. The window is *burning*. Session windows still throttle. | burn-down |
| **Placement pressure** | Of a machine, for an executor's jobs: the headroom of its binding week window — to the hard limit, or to 100% while burning — per hour left before that window resets. With reset-aware placement (`HOPPER_RESET_AWARE_PLACEMENT`, default on) a job goes to the machine with the most, then the most room, then the lowest id. 0 without a week window that names its reset. | urgency |
| **Critical priority** | `HOPPER_CRITICAL_PRIORITY` (default 100; 0: off): a job at or above it that fits on no machine may take a lane past its caps — the machine's lane cap, its executor's, or the reserved lanes — on a machine that is online, runs its executor, matches its pin, is not at its hard limit and is not over its cap already — so at most one lane over it. The lane drains when its job ends. The hopper still never preempts a job. | urgent, express |
| **High priority** | A job whose live priority is at or above the **high-priority threshold** (issue #535): the user's setting `highPriority`, default 75 — what `hopper:high` gives. Tagged (`high`) and listed first wherever jobs are listed or wait — questions, logins, lanes, Needs a person, parked jobs, the queue, the nav badges —, its runs again made first, its lane drained last under a usage limit, and it takes a free **priority lane** first. The job's *live* priority: a label change at the next sync moves it everywhere, a started job's too. A **low** job is one below the default priority (50). `priority`, `high` on its question, login, failure and hand-off in the API and in their events. | urgent, critical (*critical priority* is the over-the-cap rule) |
| **Priority lane** | One of the lanes a high-priority job gets first (issue #535): a machine's lane number (`desk/lane-2`), chosen by **lane reliability** — the most reliable, as many as the setting `count` (default 1) — or by an admin (`manual`). While no high-priority job waits it stays free (`keep-free`, the default) or takes a default job last (`share`), never a low one. A running job is never stopped for one. The decider names the lane it opens (`StartPlan.opens`). `GET /api/priority-lanes`; the settings `POST /ui/api/priority-lanes/settings`. | fast lane, reserved lane (*reserved lanes* keep room for pinned jobs) |
