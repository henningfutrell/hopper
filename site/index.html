self-hosted A job queue for coding agents

Label an issue. An agent picks it up.

job-hopper pulls jobs from GitHub issues, runs each one as a Claude Code session on a machine it manages, answers or escalates the questions a job asks, and keeps every machine inside its usage budget. One daemon. One Postgres database. One line to install. 

$ curl -fsSL https://raw.githubusercontent.com/henningfutrell/hopper/main/scripts/get.sh | bash
$ bash ~/.local/lib/job-hopper/scripts/open-ui.sh  # signs you in, opens the UI
Linux, systemd --user, Node.js ≥ 24. Bundled Postgres in docker, or bring your own: curl … | JOB_HOPPER_DATABASE_URL=postgres://… bash. Run it again to upgrade. 
$ cp deploy/hopper.env.example deploy/hopper.env  # fill it in
$ export POSTGRES_PASSWORD="$(openssl rand -hex 24)"
$ docker compose -f deploy/compose.yaml --profile container up -d --build
$ docker compose -f deploy/compose.yaml exec hopper \
    job-hopper login-code --link http://127.0.0.1:4790
The daemon in a container beside its Postgres; jobs run on machines it reaches over ssh. Behind a reverse proxy: JOB_HOPPER_PUBLIC_URL. Details in docs/deploy.md. 
$ npm ci && npm run build:ui
$ docker compose -f deploy/compose.yaml up -d postgres
$ export JOB_HOPPER_DATABASE_URL="postgres://hopper:$POSTGRES_PASSWORD@127.0.0.1:5433/hopper"
$ node src/main.ts                                         # --help: every setting
$ node src/cli.ts login-code --link http://127.0.0.1:4790  # open the link
In the foreground, for a try-out or development. TypeScript run directly by Node — no build step but the UI.

How a job moves

From a labelled issue to a closed one.

The issue body is the prompt. Nothing pushes work in: the hopper pulls it, places it, runs it and reports back through the issue's labels.

01

Label an issue

Add hopper to an issue by an author you allow. hopper:high and hopper:low set its priority.

02

It is pulled

A job source — the gh CLI or a GitHub App — picks it up. No route creates a job.

03

Routed and placed

Routing rules pin a machine, executor or priority. Otherwise it goes to the online machine with the most room left.

04

Runs as Claude Code

Each job is a Claude Code session in its own herdr pane, in a checkout of its repo on that machine.

05

Questions handled

The answerer replies to what it can. The assessor decides what a person must answer; the UI shows what waits for you.

06

Done, and closed

A finished job gets hopper:done and its issue is closed. A failed one gets hopper:failed; remove it to retry.

hopper→ hopper:claimed→ hopper:done or hopper:failed The labels say where every job is, right on the issue.
What you get

A queue that knows what each machine can take.

One decider engine over machines, lanes, usage budgets and the queue — deterministic, and every decision it makes is in the event log.

Usage budgets, enforced

Each machine reads its Claude plan usage. Under the soft limit it runs every lane; between soft and hard it scales lanes down; at the hard limit it starts nothing and drains.

Pulled, never pushed

Jobs come only from job sources, and only from authors you allow. There is no endpoint to submit one.

All state in one database

Jobs, events and config documents live in Postgres. Secrets come from the environment; the hopper stores none.

Sign-in fails closed

Login codes, passwords (argon2), OIDC, GitHub or SAML — each through an established library. No sign-in is only ever explicit.

A UI for the whole fleet

The board, questions, machines, usage, plugins, routing, webhooks, events and decisions — live.

Events and webhooks

Every change is a versioned event with a JSON schema. Subscribe with signed webhooks, retried with backoff.

An API, documented

An OpenAPI reference at /docs/ — try every route from the page. An operator CLI for the rest.

Where jobs run

Start on one host. Add machines when you want more room.

A machine has lanes: how many jobs it runs at once. Each kind is one script away, and the Machines view shows it online within seconds.

What you need
